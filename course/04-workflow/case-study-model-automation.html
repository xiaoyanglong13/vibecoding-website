Case study: the monthly close, revisited

A recurring, higher-stakes analysis task — where planning, an information environment, task specification, and memory stop being nice-to-haves and start being the reason the workflow can be trusted every month, not just this one.

Difficulty · Beginner ~45 minutes Full case: /cases/finance

The scenario

An FP&A analyst updates a three-statement model every month from a trial balance export. Done by hand, it's four to five hours of copy-paste and reconciliation, with real sign-flip mistakes along the way. The goal is the same model, refreshed in about ten minutes, with a short note explaining what changed — run again, correctly, every month.

Stage 1 · Plan

The session opens with a plan request, not a code request — the exact habit from this module's first page. The prompt names the role, the three relevant files, the steps, and the constraints that matter in practice (existing files are read-only; formula cells must stay intact):

Prompt (abridged)
You are a financial analyst. Every month you update the
three-statement model from this month's trial balance. There
are three files: trial_balance.csv, account_mapping.csv,
model_2026-03.xlsx.

1) Categorize each TB row using account_mapping. If no mapping
   exists, skip it and record it separately.
2) Sum the mapped values into the Inputs worksheet's newest
   column.
3) Existing files are read-only. Leave formula cells intact.

Before writing any code, show me the complete plan.

Reading the plan back catches the sign convention and the untouched-formula-sheets list before any code runs — exactly the two-minutes-now-versus-an-hour-later trade this module opened with.

Stage 2 · Information environment

The three files sit in one folder, and the mapping file is the one piece of real-world messiness: a few accounts are new each month, and sign convention is mixed between the general ledger and the model. Nothing here is a guideline document written in advance — the plan prompt above is the context, because the folder is small enough to describe inline. The previous page's inputs/references/outputs pattern is the same idea at larger scale.

Stage 3 · Specify the task — and place the checkpoint

The full build runs in six steps, and step six is where breaking the task down correctly matters most. Filling in known accounts is a builder step: deterministic, reusable, safe to run unattended. Deciding what an unmapped account should map to is a thinker step — a judgment call, not a formula. So when the analyst asked for the whole thing automated end to end, the agent's first version made that judgment call on its own. One more prompt fixed it:

Prompt
I need to check and approve the unmapped accounts before
adding them to the map. Make this a human checkpoint.

The script keeps the autonomy to read, summarize, and recommend; it loses the autonomy to silently edit the one file that defines how the business reports itself — the account mapping is the audit trail. That's the principle from this module's third page, applied to a real file with real consequences.

Stage 4 · Memory

The close of the session is a memory-doc prompt, almost word for word from this module's fourth page:

Prompt
Can you summarize my workflow in this session so I can do
this again next month?

What comes back is workflow.md — a prompt doc that makes next month one line instead of six prompts:

I have updated new trial_balance data for May, repeat what I
did last month following this workflow @workflow.md

The agent picks up the workflow, runs the script, pauses at the unmapped-accounts checkpoint, generates the summary, and hands back a finished model — with the one step that needs a human still needing one.
