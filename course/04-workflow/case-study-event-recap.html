Case study: the event recap, revisited

A fast, low-stakes task — a good place to see planning, an information environment, task specification, and memory work together before the more procedural case that follows.

Difficulty · Beginner ~20 minutes Full case: /cases/people

The scenario

Every case competition ends with a debrief to the club president — same sections, same tone, same length. The raw material is one teammate's messy notes; the finished document takes two or three hours to write by hand. The goal is to get that down to one session, without losing the parts that make it feel written by a person who was there.

Stage 1 · Plan

Rather than asking the agent to guess at a format, the plan here is a plan for how to learn the format: interview the user one question at a time about what a good recap needs, before writing anything.

Prompt
I'm setting up a folder for generating recurring event recap
documents. Before we write anything, ask me the questions
you'd need answered to write a good CLAUDE.md — the file
that tells you the rules for this project every time you open
it. Ask one question at a time.

This surfaces things a first-pass CLAUDE.md would have missed: whether certain sections are mandatory even when the notes are silent on them, how to handle names, what should be flagged for human review before anything goes out.

Stage 2 · Set up the information environment

The folder separates what changes each time from what stays fixed:

event-recap/
├── inputs/        (this event's raw notes)
├── references/    (last semester's approved recap — the format to match)
└── outputs/       (finished recap goes here)

The references/ folder is doing the real work. Describing the format in words and letting the agent invent the structure produces something plausible but wrong; a real example to match against does not.

Stage 3 · Specify the task

With the interview answered, the CLAUDE.md gets written together — not handed down as a fully-specified spec, and not left so vague that the agent has to guess at mandatory sections. It states the objective and the constraints that matter:

## Mandatory sections
Event overview, Results, Key learnings (min. two), What we'd
do differently, Thank-yous (always name sponsors).

## Format rules
Match references/ on structure and length. Do not invent facts
— write "[to confirm]" where the notes are silent.

Generating the recap is then a single prompt against that file and the two input documents — the task specification did the work, not a longer prompt.

Stage 4 · Memory

The payoff shows up next semester. The folder itself is the memory: references/ now includes this event's recap alongside last semester's, and the CLAUDE.md already encodes the rules that took a full interview to work out the first time. Next time, the same request runs against a folder that already knows what a good recap looks like — no re-explaining required.
