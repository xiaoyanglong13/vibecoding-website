Build project memory

A productive agent relationship shouldn't start from zero every time. As you work, capture useful workflows, rules, corrections, and progress in simple files so the agent can pick up the right context in future sessions.

Don't rely on the conversation to remember everything

During a long session, you and the agent may develop a great deal of shared context. You clarify what you want, correct mistakes, explain company rules, make decisions, and discover better ways to complete the work.

But when you start a new session, the agent doesn't automatically remember what happened in previous conversations. If something matters for future work — such as a rule, correction, workflow, or decision — you should write it down in the project so the agent can access it next time.

In this course, we'll use the word memory broadly for these persistent notes and instructions. They're often just Markdown (.md) files that live alongside the rest of your project.

What should memory preserve?

Different kinds of information are worth remembering for different reasons.

What you want to preserve Why it matters Example
A repeatable workflow You want to perform the same task again without redesigning the process. Run the same monthly sales analysis when next month's data arrives.
Rules and decisions Important requirements often emerge gradually as you work. Exclude test customers and use fiscal quarters rather than calendar quarters.
Corrections You don't want the agent to repeat the same mistake next time. “Revenue” in this project means net revenue after returns, not gross sales.
Current progress You want to stop work and resume later without reconstructing what happened. The data is cleaned and the next step is to investigate regional differences.

These notes turn useful context that emerged during one session into context that can be reused in the next.

1. Prompt docs: save a repeatable workflow

Suppose you spent time with the agent developing a process for analyzing a monthly sales file. The first time may require several rounds of prompting, planning, and correction. If the same task will happen again, save the finished workflow instead of repeating that process every month.

Ask the agent:

Summarize the workflow we used for this analysis so I can
repeat the same process when next month's data comes in.

The resulting file might look something like this:

# Monthly sales analysis

1. Load the newest file from /data/monthly-sales/
2. Exclude rows where account_type = "test"
3. Calculate sales by region and product category
4. Compare results with the previous month
5. Flag changes greater than 10%
6. Create the standard summary table and charts
7. Check totals against the source file before finishing

Next month, instead of reconstructing the process, you can point the agent to this file and ask it to run the same workflow on the new data.

2. Rule docs: preserve what you learned

Some of the most important context doesn't exist at the beginning of a project. It emerges through back-and-forth work.

You may explain a business rule, reject one interpretation of the data, or correct the agent's assumptions. If those lessons will matter again, summarize them into a rule document.

Ask the agent:

Summarize the important rules and corrections that emerged
during this session so they can be applied next time.

For example:

# Analysis rules

- Use net revenue, not gross sales, when reporting revenue.
- Exclude internal test accounts from all customer metrics.
- Our fiscal year begins in July.
- When a store has fewer than 30 survey responses, do not
  report its satisfaction score as a standalone comparison.
- Never overwrite files in /data/raw.

A correction that once existed only in conversation has now become part of the project's reusable context.

3. Running logs: remember where you left off

Memory is also useful when a project spans many sessions. You may not need a permanent rule; you simply need to remember what has already been done and what should happen next.

Ask the agent:

Summarize what we accomplished today so I can resume the
project in a future session.

A running log might contain entries such as:

# Project log

## August 19

Completed:
- Cleaned the survey data
- Matched stores to regions
- Created the first regional comparison

Decisions:
- Use median satisfaction rather than mean
- Keep stores with fewer than 30 responses out of rankings

Still unresolved:
- Whether to combine online and in-store surveys

Next:
- Compare satisfaction changes with sales changes

When you return, the agent can read the log and quickly understand the current state of the work.

Let the agent maintain the memory

You don't need to write all of these documents yourself. A useful practice is to have the agent draft and update them, while you review important changes.

At the end of a work session, a simple instruction may be enough:

Before we finish, make the necessary updates to the project
memory.

This creates a useful habit: do the work, then preserve what the next session needs to know. If nothing meaningful changed, the memory files don't need to grow.

Tip There's no single correct memory system. One project might use a single project-guide.md; another might keep separate files for workflows, rules, and progress. The names aren't important — what matters is that the information is easy for both you and the agent to find and maintain.

A special case: CLAUDE.md and AGENTS.md

Some coding agents recognize a specially named instruction file in a project. In Claude Code, the common file is CLAUDE.md. In Codex and several other agent tools, a common convention is AGENTS.md.

These files are useful because the agent looks for them automatically when it begins work in a project. They're therefore a good place for high-level instructions that should apply across many tasks.

For example, a CLAUDE.md or AGENTS.md might contain:

# Project instructions

- Read project-guide.md before beginning a new analysis.
- Never modify files in /data/raw.
- Put generated reports in /outputs.
- Use the company's fiscal calendar described in
  /rules/fiscal-calendar.md.
- Ask before deleting or replacing an existing output.

Think of this file as the agent's front door to the project. Keep the most important, broadly applicable guidance there, and point to more detailed documents when needed. Trying to put every rule, workflow, and historical detail into one giant instruction file can make the important guidance harder to find.

Tip Memory helps, but it isn't enforcement. An instruction written in a memory file is still an instruction to an LLM — the agent can misunderstand it, overlook it, or fail to follow it perfectly. Use memory to make good behavior more consistent, not to guarantee it; important requirements should still be verified, and truly critical safeguards shouldn't depend only on a sentence in a Markdown file.

Putting it together

Over time, your project can develop a small information system around the agent:

Project files
  ↓
Project guide: Where is everything?
  ↓
Workflow docs: How do we repeat common tasks?
  ↓
Rule docs: What have we learned?
  ↓
Running log: Where did we leave off?
  ↓
CLAUDE.md / AGENTS.md: What should the agent know when it starts?

This is one way an agent becomes more useful over time. The model itself doesn't need to permanently learn your project. Instead, you maintain a set of external memory files that give it the right information when it needs it.

Exercise

Return to the project you used on the previous pages. Ask the agent to create three short memory files:

  1. A workflow document for one task you may want to repeat.
  2. A rule document containing important decisions or corrections.
  3. A running log describing what has been completed and what comes next.

Then ask the agent to propose a short CLAUDE.md or AGENTS.md containing only the high-level instructions that should apply whenever it works on the project.

Review the files yourself. What belongs in long-term memory? What is temporary and should be left out?
