Memory across sessions

An agent does not check your prior conversation history every time a new session starts. Whatever it should remember has to be actively written down — and that memory can serve more than one purpose.

Memory has to be maintained, not assumed

By default, each new conversation starts from nothing. The agent that spent an hour with you last week learning your formatting preferences, your team's terminology, and the mistake it made and corrected does not carry any of that into today's session unless you gave it somewhere to read that back from. That somewhere is usually a short file, sitting in the project folder, that the agent reads at the start of a session — the same guideline-document idea from the previous page, applied over time instead of just across a folder.

Three things memory can do for you

Memory files aren't all the same kind of document. Depending on what you're trying to preserve, a memory file can be:

Type What it's for Example prompt to create it
Prompt doc Repeat the same task next time without re-explaining or re-planning it. “Summarize my workflow so I can do the same thing when next month's data comes in.”
Rule doc Capture rules and context that emerged as you went back and forth, so they apply automatically next time. “Summarize the important learnings so I can apply the same rules next time.”
Running log Record what happened in a session so you (or the agent) can pick the work back up later. “Summarize what we did so I can resume work next time.”

A single project often accumulates more than one of these. And whichever kind you're building, the habit that makes memory actually work is simple: update it after every session. A memory file that was accurate a month ago and hasn't been touched since is a file the agent will trust anyway — which is worse than no memory file at all.

Let the agent draft it, you edit

You don't have to write these files from scratch. The general practice is to ask the agent to draft the memory document at the end of a session, based on what just happened, and then read it over and correct anything it got wrong or left out before you save it. There's no fixed template for this — a prompt doc, a rule doc, and a running log all look different depending on the project — but the loop is the same one from Module 1: inspect the draft, revise it, and only then treat it as something you can rely on next time.

Tip: CLAUDE.md and AGENTS.md Many agent tools look for a specific file — commonly CLAUDE.md or AGENTS.md — and read it automatically at the start of every session in that folder, without being asked. That makes it the natural home for high-level rules and context you want applied every time. It is not a perfectly reliable rulebook — the agent may still occasionally act against a rule written there — but because it's always read, it's the right place to put anything important enough that you'd rather over-communicate than leave out.

Exercise: Turn a correction into a rule

Imagine you asked an agent to draft a client-facing summary, and it used first names for everyone — including a senior partner at the client's firm, where your team's convention is to use last names and titles for anyone outside your own company. You corrected it in the moment. Draft the few lines you'd add to a rule doc so this doesn't need correcting again next time.
