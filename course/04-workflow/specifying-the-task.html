Specify the task

Once the agent has the right context, the next step is to tell it what you want done. A good task description is clear about the objective and important requirements, without trying to micromanage every technical step.

From context to task

After you've provided the relevant context, you can specify the task you want the agent to perform. This usually includes two things:

Part of the task What it means Example
Objective What you want the agent to accomplish. “Build a dashboard that helps managers compare store performance.”
Requirements Company-specific rules, constraints, preferences, or information the agent should follow. “Use our existing sales data, keep the current branding, and don't expose customer-level information.”

You don't need to know exactly how the task should be implemented. Your job is to make the goal and important constraints clear enough for the agent to propose a sensible approach.

Use planning as part of task specification

For a non-trivial task, it's often useful to stay in plan mode while you refine the request. Instead of giving one giant prompt and immediately asking the agent to build, you can work through the task in several iterations.

Example: refining a task in plan mode

I want to add a feature to our sales dashboard that helps
regional managers identify stores that may need attention.

Before building anything, explore the current project and
propose a plan. Tell me what information you would use and
what the user would see.

The agent might respond with a proposed approach, after which you could refine it:

That's close, but don't rank stores only by sales decline.
Also consider customer complaints and missed sales targets.

Revise the plan, but don't implement yet.

This back-and-forth is useful because the first version of your task may not capture everything that matters. You may realize that the goal needs to change, that a business rule is missing, or that the agent needs additional context.

Sometimes you need to explore before you can specify the task

You won't always know exactly what to ask for at the beginning. In business problems, the task itself may need to be discovered through a little exploration or brainstorming.

Suppose your goal is:

I want managers to understand why customer satisfaction has
fallen.

That's a useful starting point, but it isn't yet a complete build request. You might first ask the agent:

Look at the available survey, complaint, and sales data.
What kinds of analyses or views could help managers understand
why customer satisfaction has fallen?

Don't build anything yet. Give me several options and explain
what information each would require.

The result may help you decide whether the right solution is a dashboard, a diagnostic report, a set of charts, a customer-segmentation analysis, or something else.

The task may reveal missing information

Planning can also expose gaps in the information environment. The agent may discover that it can't complete the task well with the data currently available.

For example, the agent might tell you:

I can compare satisfaction across stores, but I can't
determine whether wait times are contributing to the decline
because the project doesn't contain any wait-time data.

That's useful. Planning isn't only about producing a plan — it's also a chance to discover what's missing before you spend time implementing the wrong solution.

How specific should you be?

A common mistake is to assume that a good task description must tell the agent exactly how to write the code. Usually, it shouldn't.

Prompt — too prescriptive
Use Python to write a function that loops through each row,
calculates the percentage change, stores it in a new dataframe,
then uses Plotly to create a bar chart...

If those implementation details aren't important to the business objective, let the agent decide how to handle them. You can instead specify the outcome:

Prompt — states the outcome
Add a view that lets managers compare each store's sales this
month with last month. Show the percentage change clearly and
make stores with large declines easy to identify.

The first prompt tells the agent how to code. The second tells it what the solution should accomplish. For vibecoding, the second is usually more useful.

But don't be too vague

Giving the agent freedom doesn't mean giving it no direction. If a request is too vague, the agent may misunderstand the goal or use a much more complicated solution than the problem requires.

Example: using a big hammer on a small nail

Suppose you ask:

Make it easier for users to find customers.

The agent might interpret this as a major feature and build an advanced search system with multiple filters, fuzzy matching, saved searches, and a new database index.

But perhaps all you wanted was:

Add a search box above the customer table that filters the
existing rows by customer name or email address.

The agent wasn't incapable — the task was underspecified, so it had to make assumptions about the size of the solution.

A useful level of specificity

A good task description usually focuses on the business outcome, important constraints, and what a successful result should look like.

Too vague Useful specificity Too prescriptive
“Improve the dashboard.” “Make it easier for managers to see which regions are missing their monthly sales targets.” “Create a Python function called flag_regions(), then use...”
Agent must guess the goal. Agent understands the desired outcome and can choose an implementation. You're making technical decisions the agent could make for you.

A useful rule is:

Be specific about the outcome and constraints; be flexible about the implementation.

How should you break down a complicated task?

A large task can often be divided into smaller pieces, but there's no universal rule for where to split it. A useful way to think about the problem is to ask:

Where do I want a human checkpoint?

A checkpoint is a place where you want to inspect the result, make a decision, or provide additional information before the agent continues.

Example: building a customer analytics dashboard

You could ask the agent to do everything in one task:

Clean the customer data, analyze it, decide which metrics
matter, build a dashboard, and write recommendations.

But this combines several important decisions. You may want checkpoints between them:

Step 1: Inspect and clean the data.
  ↓
Human checkpoint: Do the cleaning decisions make sense?

Step 2: Analyze the data and propose useful metrics.
  ↓
Human checkpoint: Are these the metrics managers care about?

Step 3: Plan the dashboard.
  ↓
Human checkpoint: Does the proposed design answer the business question?

Step 4: Build and test the dashboard.

In other situations, you may trust the agent to complete several steps together. The right level of decomposition depends less on how many technical steps are involved and more on where human judgment is valuable.

Human checkpoints are decision points

Use a checkpoint when… Example
The agent is making an important business assumption. Deciding which customers count as “high value.”
There are several reasonable directions. Choosing between a dashboard, report, or alert system.
A mistake would affect everything that follows. Cleaning or merging data before analysis.
You need to evaluate an intermediate result. Reviewing proposed KPIs before the dashboard is built.

This gives you a practical way to break down complex work: let the agent run between points where human judgment matters.

Putting it together

Specifying a task isn't about writing the perfect prompt once. For more complex work, it's often an iterative process:

State the objective
  ↓
Add important requirements and constraints
  ↓
Explore or brainstorm if the solution is unclear
  ↓
Use plan mode to inspect the proposed approach
  ↓
Identify missing information
  ↓
Revise the task
  ↓
Choose where human checkpoints should occur
  ↓
Implement

The goal is to give the agent enough direction to solve the right problem, while still letting it handle the technical details you don't need to specify yourself.

Exercise

Imagine you have customer transaction data and want to build something that helps a marketing manager identify customers who may be at risk of leaving.

Write a task request that includes:

  1. The business objective.
  2. Important requirements or constraints.
  3. A request for the agent to plan before implementing.
  4. At least one question you want the agent to explore before deciding on the solution.
  5. One place where you would insert a human checkpoint.

Then compare your request with a very short version such as Build a churn dashboard. What assumptions would the agent have to make in the shorter version?
