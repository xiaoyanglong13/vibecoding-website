Specifying the task

With context in place, you can state what you actually want. This page covers what to include, how specific to be, and how to break a complicated task into steps without losing control of it.

What to include

Once the agent has the context, a good task specification usually has three parts: the objective (what you're trying to accomplish, not just the next action), any company- or project-specific rules the agent needs to follow (a policy, a format, a constraint that isn't obvious from the data alone), and, for anything non-trivial, a request to plan first in plan mode before doing anything (see the previous page).

Expect this to take more than one pass. Sometimes it helps to brainstorm out loud with the agent before settling on an approach — ask it to lay out two or three ways to tackle the problem and their tradeoffs, rather than assuming the first framing is right. And often the act of specifying a task is what surfaces that a piece of data is missing entirely; treat that as useful information arriving early, not as a setback.

How specific should you be?

New users tend to make one of two opposite mistakes.

Too specific: writing the solution instead of stating the problem

Suppose you need the monthly churn rate from a subscriber table. It's tempting to spell out exactly how the code should work:

Prompt — over-specified
Write a Python function called calc_churn(df). Inside it,
create an empty list. Loop over each unique month using a for
loop. For each month, use a nested loop to count how many
customer IDs from the previous month are missing in the
current month. Divide that count by last month's total and
append the result to the list. Return the list at the end.

This over-specifies the implementation and under-specifies the goal. It locks in a slow, nested-loop approach the agent would never choose on its own, and it never actually states what churn means — so if the loop logic is subtly wrong, there's no definition to check it against. A prompt that states the objective and the definition, and leaves the implementation to the agent, does better:

Prompt — states the objective
I need the monthly churn rate from this subscriber table.
Churn rate = (customers active last month who are gone this
month) / (customers active last month).

Write a script that outputs this as a table, one row per
month, and flags any month where the customer count looks
implausible (e.g. drops to zero, or jumps more than 50%).

This version tells the agent what "correct" means and lets it pick an efficient, idiomatic way to compute it — which is exactly the kind of judgment agents are good at, and exactly the kind of work you don't need to do yourself.

Too vague: a big hammer for a small nail

The opposite failure is staying so vague that the agent reaches for a disproportionate solution. Ask for "a way to track our customer data" and you may get a proposal for a database schema, an ingestion pipeline, and a set of tables — when what you actually needed was one column added to an existing spreadsheet. Losing control of scope is as real a risk as over-specifying.

The fix for both failure modes is the same: state your intention, not just an instruction or a bare request. One added sentence of intent changes the outcome:

Prompt — adds intent
I need a way to track our customer data. This is for a single
slide in tomorrow's meeting — I just need this quarter's
signups by region as a table I can paste in. This is not a
system we'll maintain going forward, so keep it as simple as
possible.

Naming the intention — a one-off slide, not a permanent system — tells the agent how much infrastructure the problem actually warrants. State the objective and the constraints, explain why you want it, and let the agent propose the approach; step in when the proposal is either more elaborate or less careful than the situation calls for.

Breaking down a complicated task

For anything with more than a couple of steps, the plan should break the work into stages — and the most important design decision is figuring out where the human checkpoint belongs.

Recall the builder-vs-thinker distinction from Module 1: when the agent is acting as a builder, producing reusable logic that should behave the same way every time, that step can usually run unattended and only needs checking once, when you first verify it works. When the agent is acting as a thinker, making a judgment call or interpreting something ambiguous, that step's output is exactly where a human checkpoint belongs — a pause before its result gets used by anything downstream.

Principle When you break a task into steps, ask of each one: is this a builder step or a thinker step? Builder steps can chain together automatically. Thinker steps need a pause for your review before the next step runs.

The monthly-close case study later in this module makes this concrete: the script that fills in known accounts is a builder step and runs on its own, but the moment it hits an account it can't classify, that's a thinker step — and the workflow is deliberately built to stop and wait for a human decision there before writing anything.

Exercise: Steps and checkpoints

Your team lead asks you to: merge three vendor spreadsheets into one master list, flag any vendor whose contract renews in the next 30 days, draft a short renewal-negotiation memo for each flagged vendor, and send the memos to the relevant account managers.

Break this into steps. For each step, decide whether it's a builder step or a thinker step, and mark where you would place a human checkpoint before letting the workflow continue.
