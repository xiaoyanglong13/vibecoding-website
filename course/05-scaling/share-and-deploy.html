Share and deploy what you build

You've built an application that works on your computer. But how can someone else use it? In this lesson, you'll publish a website with GitHub Pages, learn how to update it safely, and explore Vercel as a way to prepare for applications with AI features.

It works on your computer. Now what?

Think back to the coffee shop dashboard from Module 4. You can open it in your browser, explore charts, and change filters. The coffee shop owner asks you to send a link so they can try it.

You send http://localhost:3000. They click it, but nothing appears. Why? localhost refers to the computer where a program is running. It isn't a public address for your dashboard.

Deployment means making a version of your project available in an environment where other people can access it. Hosting is the service that makes the website available; a URL is its web address.

Before: your dashboard runs only on your computer, perhaps at http://localhost:3000.

After: you can share a website address such as https://yourname.github.io/coffee-dashboard/. Others can open it in their browsers.

These addresses are examples. Your actual URL depends on your GitHub username and repository name.

GitHub can host your website, too

In the previous lesson, you learned that Git tracks changes and GitHub stores your repository online. GitHub also has a website-hosting service called GitHub Pages. For a simple website, you may not need another platform.

Build and test locally
        ↓
Commit and push to GitHub
        ↓
Publish with GitHub Pages
        ↓
Share your website URL

GitHub Pages is well suited to static websites: websites made from HTML, CSS, JavaScript, images, and other files delivered to visitors' browsers. Static doesn't mean uninteractive. A dashboard with filters, charts, or a calculator can still be a static website if its functionality runs in the browser.

Important distinction GitHub Pages does not run a persistent application server or your own server-side Python, PHP, or Node.js code. A project requiring a backend, private database access, user authentication logic, or securely stored API credentials usually needs additional services. We return to this when discussing AI APIs in the next lesson.

Deploy a simple website with GitHub Pages

Let's use a small HTML/CSS/JavaScript project. You can use a simple dashboard, portfolio, or calculator, as long as it has no confidential data or backend requirements.

Step 1: Ask your agent to check the project

Before publishing, check what kind of project you have. A plain HTML site is the easiest place to start; frameworks may need an extra build step.

Prompt
I want to publish this project using GitHub Pages.

Before changing anything:
1. Inspect how this project runs.
2. Tell me whether it can work as a static website.
3. Identify its entry point (such as index.html),
   assets, and any build steps.
4. Check for private data, passwords, and API keys.
5. Propose the simplest safe deployment plan.

Do not make the repository public or publish anything
without my approval.

Step 2: Put the website on GitHub

Use what you learned on Page 1 to commit the verified project and push it to a GitHub repository. For the simplest example, put index.html in the repository's root folder, alongside any necessary CSS, JavaScript, and assets. A basic project might look like this:

coffee-dashboard/
├── index.html
├── styles.css
├── script.js
└── data/
    └── sample-sales.csv

Notice that the data file will be part of the published website if the page uses it. Use only data that is safe to make public.

Step 3: Turn on GitHub Pages

  1. Open the repository on GitHub and select Settings.
  2. In the sidebar, open Pages.
  3. Under Build and deployment, choose Deploy from a branch.
  4. Select the branch containing your website (often main) and the /(root) folder; then click Save.
  5. When publishing finishes, open the site URL shown in Pages settings.

For a project site, the default address is usually https://USERNAME.github.io/REPOSITORY/. Publishing can take a few minutes. See the official GitHub Pages instructions if the interface changes.

Tip If your site uses React, Vite, or another framework that requires a build, ask your agent whether you need a GitHub Actions deployment workflow. Publishing the source files directly may not work. Also check links and asset paths: a project site lives under /REPOSITORY/, not necessarily at the domain root.

Update a website after it's published

Now the coffee shop owner asks for a weekday-sales chart. You make the change locally with your agent, test the dashboard, and push the verified changes to the published branch. GitHub Pages can then publish the updated website automatically.

Edit locally → Verify → Commit → Push → Check live site

This is why the previous lesson mattered. Your commits record what changed, and the published site reflects a version of that project. A successful push doesn't guarantee the live website works correctly: open the public URL and test it again.

If publishing doesn't work

Don't ask the agent to randomly change settings. Check the repository's Actions tab and the Pages settings for build or deployment errors. If the page loads but its styles or data are missing, inspect relative file paths and browser errors.

Prompt
My GitHub Pages site is not working as expected.

Help me diagnose it systematically.
1. Ask me for the site URL and any relevant error logs.
2. Compare the published site with the local project.
3. Check the entry point, build output, and asset paths.
4. Explain the most likely cause and propose a fix.

Do not change settings or files until we agree on a fix.

Before you share: Check what others can see

Publishing is not just a technical step. Once others can open your application, you have to think about its data, functionality, and audience.

  • Data: Remove confidential information and use anonymized or sample data. Files served by a public site can generally be downloaded by visitors.
  • Secrets: Never publish API keys, passwords, or private credentials in website files. Moving a key into browser-side JavaScript or a frontend environment variable does not make it secret.
  • Access: A GitHub Pages website is generally publicly accessible. A private repository does not automatically make the published site private.
  • Functionality: Test the actual URL in another browser or on another device. Check charts, links, mobile layout, and data loading.
  • Maintenance: Know which repository and branch power the live site, and be aware of hosting limits and any costs associated with additional services.
Remember Only publish a project that you are comfortable sharing publicly. GitHub Pages is a good learning platform for public demonstrations, not a substitute for access control when an application contains sensitive business information.

Going further: Deploy with Vercel

GitHub Pages is a good starting point, but you'll eventually want to build applications that do more than run code in a visitor's browser. For example, the next lesson will explore adding an AI feature that sends a request to a language model. That usually requires a server-side component so your API key isn't exposed to visitors.

Vercel is another hosting and deployment platform. Like GitHub Pages, it can publish a simple website. Unlike GitHub Pages, it also supports server-side functions that can communicate with APIs and other services. You can keep your code on GitHub and connect the same repository to Vercel. You do not need to abandon Git or GitHub.

Two ways to publish the same project:

Local project
    ↓
GitHub repository
    ├──→ GitHub Pages  → Static website
    └──→ Vercel        → Website + optional server-side functions

For now, both can serve your simple dashboard. Later, Vercel can also run a backend function that makes an AI API call without placing the API key in the website's browser code.

Try deploying your GitHub project on Vercel

You can use the same repository from the GitHub Pages exercise. The steps below are a first introduction, not a requirement to build a backend today.

  1. Go to vercel.com and create an account or sign in.
  2. From the Vercel dashboard, choose to create a New Project and connect GitHub when prompted.
  3. Import the repository containing your website. Review the root directory, framework, and build settings. Simple static projects may need little configuration; some frameworks require a build command and output directory.
  4. Click Deploy. When the deployment succeeds, open its *.vercel.app URL and test your website.
  5. Make a small verified change and push it to GitHub. Observe how Vercel deploys the updated version. With a Git-connected project, branches can also generate preview deployments.

See Vercel's Git deployment guide for the current interface and configuration steps.

Prompt
I deployed this website with GitHub Pages. Now I want
also to deploy it on Vercel, using the same GitHub repo.

1. Inspect the project and tell me if it is Vercel-ready.
2. Identify the framework, root folder, build command,
   and output directory, if any are needed.
3. Explain which Vercel settings I should choose.
4. Check for files or data that must not be published.
5. Help me test the deployed URL once it's live.

Do not create accounts, change permissions, or deploy
anything without my approval.

Why Vercel matters for the next lesson

Suppose you add a button to your coffee shop dashboard labeled Summarize this month's sales with AI. The browser needs to send the request somewhere. In a common architecture, a server-side function receives the request, calls the AI provider using a secret API key, and sends the result back to the browser.

User's browser → Your Vercel function → AI API
       ↑                                    │
       └──────── AI-generated summary ──────┘

Vercel lets you configure environment variables for server-side code, rather than putting secrets directly in browser JavaScript. But remember: environment variables included in client-side builds are not secret, and a secure design also needs appropriate authorization, input limits, and cost controls.

For now You don't need to set up an AI API or add a server-side function on this page. The goal is to see how GitHub and Vercel fit together, deploy a familiar project, and understand why you'll use Vercel when you add AI to your application in the next lesson.

Exercise: Publish and update a website

Choose a simple static project—perhaps a dashboard or calculator built earlier in the course. Work through the following steps:

  1. Ask your agent to inspect the project and confirm that it can be deployed through GitHub Pages.
  2. Check for private data and secrets. Commit and push the verified website to GitHub.
  3. Enable GitHub Pages and open the published site.
  4. Visit the link from another browser or device and verify that the key features work.
  5. Make one small visible change (such as editing a heading), test it locally, push it, and confirm the live site updates.

Optional extension: Import the same GitHub repository into Vercel, open its new URL, and compare what the two deployment platforms do. You do not need to add AI functionality yet.

Reflection: What changed when your project moved from your computer to a public URL? Why might you choose Vercel instead of GitHub Pages for an application with an AI feature? What responsibilities do you have now that other people can use it?
